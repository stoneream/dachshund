# セキュリティテスト設計

安全要件を、誰が、どの対象へ、どの状態で、何を試し、何を観測すれば合否を判断できるかへ変換する。ツール名の列挙ではなく、システムの境界と失敗条件に合うテスト層を選ぶ。

## 境界

- 脅威の発見とリスク判断は `threat-modeling`、安全要件をコードや設定へ反映する作業は `software-security-implementation` の範囲とする。
- 既存の実装や設定で脆弱性が成立するか判断する場合は、各分析スキルを使用する。
- 許可されていない侵入的テスト、本番環境への負荷、実データの取得を計画または実行しない。
- スキャナーを実行すること自体を完了条件にせず、期待する拒否、状態、副作用、監査記録を定義する。
- 外部環境やテスト用のアクターとクレデンシャルを用意できない場合は、代替証拠と残る不確実性を分離する。

## 参照

対象の安全要件、主要なアクター、テスト可能な境界を把握した後、設計前に[セキュリティテスト設計チェックリスト](references/test-design-checklist.md)を読む。出力前に、異常系テスト、権限、業務状態、サプライチェーン、リリース判定基準、証拠を再確認する。

## 進め方

1. 脅威、悪用ケース、安全要件、実装した対策、過去のインシデントから検証する不変条件を抽出する。
2. テストのアクター、クレデンシャル、テナント、オブジェクト、状態、入力、環境を定義する。
3. 単体、コンポーネント、統合、E2E、静的解析、動的検査、構成検査のどこで最小かつ確実に観測できるか決める。
4. 許可・拒否、順序変更、再送、競合、資源の濫用、対策の失敗を含むテストケースを作る。
5. 期待結果、許されない副作用、ログ・監査記録、後片付けを定義する。
6. 実行頻度、CIの判定基準、所有者、失敗時の扱い、証拠の保持を決める。

## 出力

- 対象と安全上の不変条件
- テストケース一覧。各ケースにアクター、前提条件、操作、期待結果、観測点、後片付けを含める
- テスト層、フィクスチャ、テスト用のアクターとクレデンシャル、環境、実行順序
- CI・リリースの判定基準、失敗時の切り分け、証拠
- 実行できないテスト、代替検証、残留リスク
