# セキュリティテスト設計チェックリスト

安全要件を具体的な合否判定へ変換するために使用する。一般的な攻撃用入力を網羅するのではなく、対象の入力、権限、状態、データフローで対策が強制されることを確認する。

## テスト条件

- 検証する脅威または安全上の不変条件を一文で示せるか。
- アクター、クレデンシャル、ロール、テナント、対象オブジェクト、開始状態を定義したか。
- 操作、期待する状態コード・応答・状態、許されない副作用を定義したか。
- 拒否だけでなく、正当な利用を壊していないことを確認する正常系があるか。
- ログ、監査記録、メトリクス、アラートなど、セキュリティイベントの観測点を定義したか。
- テスト後のデータ、クレデンシャル、外部への副作用を後片付けできるか。

## 認証・認可

- 機能または操作、ロール、オブジェクトやデータ、テナント、状態を軸として表現したか。
- 未認証、期限切れ、失効済み、対象サービス不一致、回復中などクレデンシャルの状態を含めたか。
- 水平、垂直、テナント間の越境をオブジェクトごとに拒否できるか確認したか。
- 読み取り、作成、更新、削除、共有、エクスポート、管理、一括処理を別操作として扱ったか。
- UI、公開API、内部API、ジョブ、Webhookなど全入口で同じ規則を確認したか。
- 認可規則またはAPI契約の変更とテストケース一覧を同期できるか。

## 業務ロジックとトランザクション

- ワークフローの省略、順序変更、重複、再送、期限切れ、取消後の実行を確認したか。
- クライアント由来の価格、所有者、ロール、テナント、承認、状態を改変するケースがあるか。
- 同時リクエスト、複数端末、複数アクターによる競合と、検証後から利用までの状態変化を確認したか。
- 単回トークン、クーポン、クレジット、承認、支払いが一度だけ使用されるか確認したか。
- 機能単位の実行回数、利用枠、上限と、正当利用への影響を確認したか。
- 失敗時に部分更新、二重実行、監査記録のない副作用が残らないか確認したか。

## 入力、ブラウザ、API

- 検証前後の復号、正規化、値の割り当て、直列化を通るケースを選んだか。
- 出力文脈、オリジン、Cookie、CSRF、リダイレクト、ファイルのライフサイクルなど対象ブラウザの境界を確認したか。
- RESTのメソッド・コンテンツ形式・リソース、GraphQLの深さ・処理コスト・一括処理・フィールド認可を確認したか。
- WebSocketとgRPCの接続確立、ストリーム、メッセージサイズ、セッション失効、メッセージ単位の認可を確認したか。
- タイムアウト、件数、入れ子、並列数、応答サイズなど資源上限を安全な環境で確認したか。
- テスト用入力が外部システム、実際の利用者、本番データへ影響しないか確認したか。

## サプライチェーンと設定

- ワークフローの起動条件、フォークからの入力、秘密情報、ランナー、外部提供のCIアクションやプラグインの危険な組み合わせを検出する静的検査があるか。
- ロックファイル、解決済み依存関係、SBOM、成果物のダイジェスト、生成記録の整合を確認するテストがあるか。
- 未検証の成果物、署名不一致、許可していない発行者、古いリリースのデプロイを拒否することを確認するか。
- セキュリティ検査やテストを省略、失敗許容、条件分岐で迂回できないことを確認するか。
- デプロイ承認がリビジョン、成果物、環境、引数へ結び付いていることを確認するか。

## テスト層と判定基準

- 副作用のない規則や入力検証は単体、アクター・ストレージ・キューをまたぐ処理は統合、利用者フローはE2Eなど、最小の有効なテスト層を選んだか。
- 静的解析、構成検査、実行時テストの重複と、それぞれで検出できない範囲を説明できるか。
- 必須テストを、短時間で終わるPRの検査と、時間のかかる定期・リリース時の検査へ分ける必要があるか。
- 不安定なテスト、外部依存、時刻、乱数、並行性を制御できるか。
- 判定失敗時にマージまたはデプロイを停止し、所有者と切り分け手順を示せるか。
- 過去に成立した問題の再現手順を、回帰テストとして残す条件があるか。

## 完了確認

- リスクの高い脅威に対応する各不変条件に、少なくとも一つの直接観測できるテストがある。
- 正常系と異常系の両方があり、検証結果が常に成功する作りになっていない。
- テスト用のアクター、クレデンシャル、フィクスチャ、秘密情報、環境の準備と後片付けを実行できる。
- 実行できない検証、代替証拠、残るリスクを明示している。
