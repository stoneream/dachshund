# プロダクト体験ドキュメント作成・更新スキル

このスキルは、サービスや機能の初期コンセプトを、ユーザー種別ごとの体験として整理するための手順を提供する。
実装詳細を固める前に、誰が、どこから始め、何を判断し、どの状態で完了するのかを明確にする。

## 有効化するタイミング

- 新規サービスや新機能の初期コンセプトを体験ベースで整理する場合
- 申請者と承認者、出品者と購入者、管理者と一般利用者など、複数のユーザー種別がある場合
- ユーザーフロー、シーケンス図、ステップ別画面ユースケース図、画面遷移図の作成や整理を求められた場合
- 抽象的な機能名や操作名を、ユーザーが実際に行う行動へ言い換える必要がある場合
- 図が増えて元のコンセプト文書が読みにくくなっている場合

## 適用しないタイミング

- API、DB、ジョブ、権限などの実装設計の整理を目的とする場合
- 完成済み仕様の正誤確認やレビューを主目的とする場合
- UI のビジュアルデザイン、画面モック、コンポーネント設計が主目的の場合
- 単純な文章校正や要約のみを行う場合

## 境界

- 対象文書を編集する場合は、既存文書の語彙、構成、リンク方針を維持する。
- 実装計画やシステム構成の決定は分離し、このスキルでは体験上必要な要件までを整理する。
- 既存文書の問題点の指摘を行う場合は、体験ドキュメントの新規構成を押し付けない。

## 参照

ユーザー種別と完了条件を特定した後、体験を整理する前に[体験整理チェックリスト](references/experience-checklist.md)を読む。図を作成または更新する場合は、図の種類を決める前に[図の作成ガイド](references/diagram-guide.md)も読む。出力前に、開始、判断、状態変化、例外、完了が対象ユーザーごとに追跡できるか再確認する。

## 基本方針

最初にユーザー種別、目的、入口、完了条件を確認する。
そのうえで、文書は原則としてユーザー種別ごとに並べる。

図は、元のコンセプト文書へ無理に詰め込まない。
図の量が多い場合は、別ファイルに分離し、元文書から相対リンクで参照する。

本文では、サービス固有の概念、前提、制約を説明する。
図では、分岐、順序、責務、状態変化を表す。
利用デバイス、提供形態、外部サービス連携などの補足は、図に入れるとかえって読みにくい場合は本文で扱う。

## 進め方

1. 対象文書と周辺文書を読み、サービスの目的、ユーザー種別、主要な完了条件を把握する
2. ユーザー種別ごとに、開始地点、入力、判断、完了状態、例外や離脱を整理する
3. 図を対象文書に置くか、別ファイルに分離するかを判断する
4. ユーザー体験、システム処理、画面責務を混ぜずに図を作る
5. 重複する図を削り、各図の役割を明確にする
6. 抽象的な文言をユーザー行動として自然な表現へ直す
7. Mermaid や Markdown の構文を確認し、横長すぎる図は縦方向や段階分割で読みやすくする

## 文書構成

複数のユーザー種別がある場合は、次の順序を基本にする。

```markdown
# 機能名 体験整理

この文書の目的と、元になるコンセプト文書への参照を書く。

## ユーザー種別 A

### シーケンス図

### ユーザーフロー

### ステップ別画面ユースケース図

## ユーザー種別 B

### シーケンス図

### ユーザーフロー

### ステップ別画面ユースケース図
```

見出し名は対象文書の語彙に合わせる。
「申請者」「承認者」「出品者」「購入者」といった、利用者視点で理解しやすい名前を優先する。

## 図の使い分け

### ユーザーフロー

ユーザーがどの順序で画面や判断を進むかを表す。
ユーザー視点の流れを扱い、内部処理の詳細は入れすぎない。

ユーザー操作のみを並べたシーケンス図と内容が重複する場合は、原則としてユーザーフローを残す。

### シーケンス図

システム、外部サービス、永続化対象、状態更新の関係を表す。
ユーザー操作を起点にしてよいが、主目的はシステム側の処理理解に置く。

ユーザーが見ている画面上の細かい遷移や説明は、シーケンス図に入れすぎない。

### ステップ別画面ユースケース図

画面やステップごとに、その画面でユーザーが何をするかを表す。
抽象的なユースケース名ではなく、実際の入力、選択、確認、申請、承認、完了確認などの行動に分解する。

ステップ別画面ユースケース図が横長になる場合は、`flowchart TD` を優先する。
1 つの図に詰め込みすぎる場合は、ユーザー種別や主要ステップごとに分割する。

### 画面遷移図

画面の前後関係そのものが論点となる場合に作る。
ユーザーフローやステップ別画面ユースケース図と重複し、かえって紛らわしい場合は作らない。

## 文言整理

機能名や内部概念をそのまま操作名にしない。
ユーザーが実際に行う行動として読める表現へ置き換える。

### 推奨

- `作成する` よりも、何を確定するのかを書く
- `登録する` よりも、アカウント作成、プロフィール作成、初回設定などの違いを書く
- `処理する` よりも、保存する、申請する、承認する、購入する、公開するなどの行動を書く
- `完了する` で終わらせず、何が完了した状態なのかを書く

### 非推奨

- 内部エンティティ名を、そのままユーザー操作として扱う
- 同じ意味の文言を図ごとに言い換える
- 一時状態と確定状態の区別を曖昧にする

## Mermaid 記述方針

- 図は Markdown 内の Mermaid コードブロックで管理する
- ノード ID や participant alias は英数字にして、表示名に日本語を使う
- Mermaid の予約語や一般語と衝突しやすい alias は避け、用途が分かる alias に具体化する
- 横長で読みにくい図は `flowchart LR` から `flowchart TD` へ変更する
- サブグラフは主要ステップや画面単位で区切る
- 同じ粒度の項目は同じ表現形式に揃える
- Mermaid の構文エラーが出た場合は、該当行の alias、矢印、ラベル、全角記号、予約語衝突を優先して確認する

## 完了確認

- 対象文書から図ファイルへリンクされている
- ユーザー種別ごとに、開始、判断、完了、例外または離脱が読める
- ユーザーフロー、シーケンス図、ステップ別画面ユースケース図の役割が重複しすぎていない
- 抽象的な操作名が、ユーザー行動として自然な文言に直っている
- Mermaid 図が横長すぎず、Markdown として読める
- 元文書と図ファイルの語彙が揃っている
