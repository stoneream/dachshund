# コーディング規約の設計

プロジェクトで繰り返し判断が割れる事項を、実装と自動検証へ接続できる規約として整理する。

## 適用範囲

- 新しいコーディング規約やスタイルガイドの作成
- 既存規約と実装慣習の不整合の整理
- 複数の選択肢からチーム標準を決めるための比較
- lint、formatter、静的解析へ移せる規約の検討

通常のコード作成やレビューでは、既存のプロジェクト規約と周辺実装に従う。このスキルを一般的な品質チェックリストとして自動適用しない。

## 参照

規約化する領域を特定した後、候補を比較する前に[規約領域カタログ](references/standards-catalog.md)の該当節を読む。出力前に、採用する規約の理由、例外、自動検証方法を確認する。カタログの項目をプロジェクト固有の根拠なく規則へ変換しない。

## 進め方

1. 既存の規約、formatter、lint、型検査、CI設定を確認する。
2. 代表的な実装を読み、文書化された規約と実際の慣習を分けて把握する。
3. 解決したい具体的な判断の揺れや失敗を特定する。
4. 候補ごとの可読性、変更容易性、既存コードへの影響、自動検証可能性を比較する。
5. 採用する規約、適用範囲、例外、移行方法を定義する。
6. 機械的に検証できる規約は、文書に加えて設定や自動化への反映を提案する。

## 規約を検討する領域

すべてを一律に規定せず、実際に判断の揺れや不具合が生じている領域を選ぶ。

### 命名と可読性

- 名前が表す責務、真偽値、単位、状態、ライフサイクル
- 公開要素と内部要素の命名、ファイルやモジュールの配置
- コメントやドキュメントを必要とする条件と、実装から自明な説明の扱い

### 責務と依存関係

- 関数、型、モジュール、レイヤーが担う責務と依存方向
- 重複を許容する条件と、共通化や抽象化を行う条件
- 外部ライブラリ、グローバル状態、依存注入の扱い

### インターフェースとデータ

- 公開API、型、戻り値、nullや省略値、エラー表現の一貫性
- 入力検証、型や形式の変換、状態変更、永続化の境界
- 互換性を維持する対象と、破壊的変更を許容する手順

### エラー処理とログ

- 捕捉、再送出、回復、再試行、終了を選ぶ基準
- 利用者向けメッセージと調査用情報の分離
- ログレベル、構造化項目、相関ID、秘密情報や個人情報の扱い

### テスト

- 単体、統合、E2Eの責務分担と必要になる条件
- 正常系、境界値、異常系、回帰条件の表現
- テスト間の独立性、時刻や乱数の制御、外部依存の置き換え方

### セキュリティと性能

- 入力、認証認可、秘密情報、依存関係について共通化すべき安全上の不変条件
- 性能要件を設ける対象、計測方法、最適化を許容する根拠
- セキュリティや性能の専門的な判断を、一般的なスタイル規約へ混在させないための境界

## 規約の基準

- プロジェクトの言語、フレームワーク、既存設計に適合する。
- 守る理由と、違反した場合の具体的な不利益を説明できる。
- 「常に」「禁止」などの強い表現は、例外なく必要な場合に限定して使う。
- 行数やネスト数などの閾値を根拠なく固定しない。
- 一般原則を列挙する代わりに、このプロジェクトで必要な判断を記述する。
- ユーザーの承認手順や作業権限を、コーディング規約へ混在させない。

## 出力

規約案ごとに、対象、規則、理由、推奨例、非推奨例、例外、自動検証方法を必要な範囲で示す。既存コードの一括変更が必要な場合は、規約の決定と移行作業を分けて提案する。
