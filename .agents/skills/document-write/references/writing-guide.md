# 文章作成ガイド

既存文書がある場合は、その文体、語彙、見出し構成、リンク方針を優先する。このガイドは既存規約がない事項の判断に使用する。

## 目的と読者

- 読者が文書を読む理由と、読後に実行または判断できる状態を決める。
- 人間、AIエージェント、開発者、運用者、利用者のうち、主な読者を特定する。
- 読者が持つ前提知識と、文書内で説明する前提を分ける。
- 一つの文書へ複数の目的を混在させず、必要な場合は相互リンクで分離する。

## 情報の根拠

- 実装、設定、テスト、一次情報から確認できた事実を書く。
- 推測、予定、現況、決定事項を明確に区別する。
- 外部仕様を説明する場合は、主張を直接支える一次情報へリンクする。
- 生成物を変更する場合は、生成元を正規の情報源として更新する。
- 一時的な回避策には理由、影響、撤去条件、追跡先を記載する。

## 構成

- 読者の作業順または判断順に見出しを並べる。
- 節の内容と粒度を予測できる見出し名を付ける。
- 見出し階層は浅く保ち、分類名の下に説明が続く場合は太字ラベルではなく見出しを使用する。
- 背景説明が長い場合も、読者が必要な操作や結論へ到達できる導線を作る。
- 同じ情報を複数文書へ複製せず、正規の記載場所へリンクする。

## 段落、箇条書き、表、図

- 単一の論点や因果関係は段落で説明する。
- 同列の複数項目、手順、確認事項、規約は箇条書きを使用する。
- 複数対象の同じ属性を比較する場合は表を使用する。
- 順序、分岐、責務、状態変化が文章だけでは追いにくい場合は図を使用する。
- 一項目のみの箇条書きや、文章を細切れにする箇条書きを避ける。

## 表現

- 抽象的な動詞を避け、入力、操作、判断、結果を具体化する。
- 目的を示す補助表現を避け、「維持する」「防ぐ」「明確にする」など、操作や状態を直接表す動詞を使う。
- 同じ概念へ同じ用語を使い、類義語による不要な言い換えを避ける。
- 主語や対象が曖昧になる受動表現を減らす。
- 「適切に」「必要に応じて」などの表現には、判断条件を添える。
- 禁止、必須、常時などの強い表現は、例外なく必要な場合に限定する。

## 日本語と用語

- 既存文書の用語と利用者が指定した表記を先に確認し、同じ概念には同じ語を使う。
- 英文や外部資料を参照する場合も単語単位で置き換えず、文脈上の対象、動作、関係を日本語の文として書き直す。
- 直訳すると意味が曖昧になる複合語は、対象、動作、関係が分かる表現へ言い換える。
- 技術分野で定着した用語や固有名詞は、分かりにくい直訳へ置き換えない。一方、一般的な語を原文に引かれて英語のまま残さない。
- カタカナ語や専門用語だけでは成果物の内容や形式が伝わりにくい場合は、読者が判断できる表現へ言い換える。
- コード識別子、コマンド、設定キー、製品名は原表記を保ち、説明文中の一般語と区別する。
- 執筆後に文章を続けて読み、主語と述語、助詞、修飾先、名詞の連続に不自然さがないか確認する。

## コード、コマンド、設定例

- 現在の実装や対応バージョンで再現できる例を使用する。
- 実行ディレクトリ、前提条件、必要権限、期待結果を必要な範囲で示す。
- パスワード、トークン、個人情報、実在する接続先を例へ含めない。
- 省略記号がそのまま実行できないことを明確にする。
- 危険な操作は対象と影響を具体化し、復旧方法がある場合は併記する。

## 日本語Markdown

- 段落内の改行は文章のまとまりで行い、原則として句点の後へ置く。
- 強制改行が必要な場合はMarkdownの規則に従う。
- 見出しへ番号を付ける場合は、既存文書の方針に従う。
- 日本語と英数字の空白は、既存文書の規則へ合わせる。
- コード識別子、パス、コマンド、設定キーはコード表記にする。

## 更新と保守

- 実装変更に伴うREADME、設計書、API文書、運用手順への影響を確認する。
- リンク、見出しアンカー、図、例、生成手順が更新後も有効か確認する。
- 変更点を文書内の複数箇所へ散らさず、責務に合う節へ統合する。
- 将来の更新者が、情報源と更新方法を追跡できる状態にする。

## 完了確認

- 読者、目的、前提、完了状態が明確である。
- 実装や一次情報と矛盾していない。
- 手順と例を必要な範囲で再現確認している。
- 既存文書との重複、用語の揺れ、直訳調、不必要な英語表現、壊れたリンクがない。
- 未確認事項や決まっていない事項を断定していない。
