# コードレビューチェックリスト

変更または指定コードに関係する節を使用する。各項目は問題の存在を前提にせず、成立条件、影響、根拠が確認できる場合に限って指摘へ変換する。

## 仕様と正しさ

- 要件、ビジネスルール、公開契約と実装結果が一致しているか。
- 正常系に加え、空値、境界値、最大値、不正値で意図した結果になるか。
- 条件分岐、比較、丸め、時刻、タイムゾーン、文字コード、単位が正しいか。
- 既存の正常な利用経路を変更または拒否していないか。
- 失敗を成功として扱う経路や、成功を失敗として扱う経路がないか。

## データと状態

- 入力検証と正規化が、データを信頼する境界で行われているか。
- 型変換や形式変換で精度、意味、識別情報を失っていないか。
- 状態遷移が許可された順序に限定されているか。
- 複数の書き込みが必要な処理で、部分成功や不整合が残らないか。
- 再送、再試行、重複イベントに対して冪等性が必要か。
- 既存データ、旧スキーマ、移行途中のデータを扱えるか。

## エラー処理と回復

- エラーを握りつぶしたり、意味の異なるエラーへ誤変換したりしていないか。
- 利用者向けメッセージと調査用情報が適切に分離されているか。
- タイムアウト、再試行、キャンセル、フォールバックが互いに矛盾しないか。
- 失敗時にファイル、接続、ロック、プロセス、トランザクションを解放できるか。
- 復旧不能な失敗を無制限に再試行しないか。
- 部分成功後の補償、再開、再実行の挙動が明確か。

## インターフェースと互換性

- 公開API、型、イベント、CLI、設定、保存形式の契約を変更していないか。
- 必須項目、既定値、列挙値、エラー形式、順序の変更が利用者へ影響しないか。
- 呼び出し元、生成コード、シリアライズ、移行処理が変更へ追従しているか。
- 旧新バージョンが混在する期間の読み書きが成立するか。
- 非推奨化、互換レイヤー、撤去条件が必要か。

## 並行性と非同期処理

- 共有状態への読み書きに競合や取りこぼしがないか。
- 更新が複数操作へ分割され、非原子的な中間状態を公開していないか。
- コールバック、Future、Promise、イベントの完了や失敗を待ち忘れていないか。
- キャンセル、タイムアウト、再試行後に古い処理が状態を上書きしないか。
- 順序保証を前提にしている箇所で、その保証が実際に存在するか。

## 性能とリソース

- 実際の入力規模や呼び出し頻度で、計算量やメモリ使用量に問題がないか。
- N+1、ループ内I/O、不要な外部API呼び出し、重複計算がないか。
- 無制限な読み込み、キュー、並列実行、キャッシュ増加がないか。
- 接続、スレッド、ファイル記述子、バッファを保持し続けないか。
- 最適化によって正しさ、可読性、観測可能性を損なっていないか。

## ログと運用性

- 障害、重要な状態変化、外部連携失敗を追跡できる情報があるか。
- ログレベル、構造化項目、相関IDが周辺実装と整合しているか。
- パスワード、トークン、セッション、個人情報を記録していないか。
- ログ出力の失敗や過剰量が主要処理を停止させないか。
- メトリクス、アラート、運用手順へ変更が必要か。

## セキュリティ境界

- 信頼できない入力が検証され、出力先に応じてエスケープされているか。
- 認証、認可、所有権、テナント境界を処理ごとに確認しているか。
- 変更した権限境界や状態遷移について、許可されない経路、再送、競合をテストしているか。
- 秘密情報や機微データが不要な範囲へ渡っていないか。
- 危険なデシリアライズ、動的実行、パス操作、外部接続を導入していないか。
- 専門的な脆弱性分析が必要な問題を通常レビューだけで断定していないか。

## 可読性と保守性

- 名前、責務、抽象度が周辺実装と整合し、意図を誤解しにくいか。
- 一つの変更理由に関係しない責務が混在していないか。
- 重複、強い結合、暗黙の前提によって変更箇所が増えていないか。
- 単純な実装で足りる箇所へ過剰な抽象化や拡張点を追加していないか。
- コメントがコードの言い換えではなく、制約や判断理由を説明しているか。
- プロジェクトの規約、自動整形、静的解析へ反していないか。

## テスト

- 変更の正常系、境界値、異常系、回帰条件をテストしているか。
- 検証式が変更結果を実際に観測し、常に成功する形になっていないか。
- 実装詳細へ過度に結合せず、利用者から見える契約を確認しているか。
- モックが実環境の型、エラー、順序、タイミングを隠していないか。
- 時刻、乱数、並行性、共有状態による不安定さがないか。
- テストを追加できない場合に、代替検証と残る不確実性が示されているか。
- 既存の回帰テスト、認可テスト、セキュリティ検査を削除、弱体化、迂回していないか。

## 指摘化の条件

- 問題が成立する具体的な入力、状態、環境、順序を説明できる。
- 利用者、データ、運用、保守へ生じる影響を説明できる。
- 対象ファイルと該当箇所に根拠を示せる。
- 好みや一般原則の不採用のみを理由にしていない。
