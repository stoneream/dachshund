# ドキュメントレビューチェックリスト

文書の目的、対象読者、正規の情報源に関係する項目を使用する。好みの文体ではなく、誤操作、誤解、更新負担につながる問題を優先する。

## 情報源

- 文書が依拠する実装、設定、API、外部仕様、運用手順を特定する。
- 正規の情報源と生成物を区別する。
- 対象ブランチ、リリース、製品版、環境が文書の前提と一致しているか確認する。
- 一次情報を確認できない内容は断定せず、未確認事項として扱う。

## 技術的正確性

- コマンド、引数、設定キー、環境変数、パスが実在する。
- コード例、設定例、API例が現在の構文と型に適合する。
- 既定値、前提条件、権限、依存関係が実装と一致する。
- 図の責務、順序、データフロー、状態遷移が実装と一致する。
- エラー、終了コード、失敗時の挙動が正しく説明されている。
- 外部リンクと参照先が主張を直接支えている。

## 完全性

- 読者が開始するための前提条件と入力が揃っている。
- 手順の各段階で期待する結果と完了条件が分かる。
- 境界値、例外、失敗時、復旧、ロールバックが必要な文書で欠けていない。
- 新しい設定、権限、依存関係、データ移行、運用変更が反映されている。
- 関連するREADME、API文書、設計書、運用手順への追従漏れがない。

## 最新性

- 廃止済みのAPI、画面、設定、手順、スクリーンショットが残っていない。
- 現行版と旧版の説明が混在していない。
- 他文書と内容が重複する場合、どちらが正規の情報源か分かる。
- バージョン固有の内容に対象バージョンが示されている。
- 更新日だけを根拠に最新と判断していない。

## 構成と導線

- 文書の責務が一つの利用目的へ集中している。
- 読者が必要な情報へ見出し、目次、リンクから到達できる。
- 前提、手順、結果、補足の順序が利用場面に合っている。
- 用語、見出し階層、記法、文体が周辺文書と整合している。
- 同じ内容を複数箇所で独立して保守する構成になっていない。

## 可読性と実用性

- 対象読者に必要な前提知識が明示されている。
- 段落、箇条書き、表、図、コードブロックが内容に合っている。
- 重要な制約や危険な操作が長い説明へ埋もれていない。
- 手順が実行順に並び、途中状態から再開する条件が分かる。
- 抽象語だけでなく、読者が行う操作や判断が具体化されている。

## 保守性

- 実装から生成できる情報を手作業で重複管理していない。
- 変更時に更新する場所と生成手順が追跡できる。
- 一時的な回避策に撤去条件や追跡先がある。
- 環境固有の値を固定例として誤解させない。
- 将来の変更で壊れやすい行番号、画面位置、出力全文へ過度に依存していない。

## 文書種別ごとの追加観点

### README

- プロジェクトの目的、主要入口、最短の開始方法が分かる。
- 詳細文書への導線があり、READMEへ全情報を詰め込んでいない。

### セットアップ手順

- 対応環境、必要な権限、依存バージョン、秘密情報の準備が分かる。
- 初回実行後の確認方法と、代表的な失敗の切り分けがある。

### API文書

- 認証、入力、出力、エラー、ページング、制限、互換性が説明されている。
- 例がスキーマと一致し、機微情報を含んでいない。

### 設計文書

- 目的、制約、採用判断、代替案、不変条件が説明されている。
- 現況説明と将来案が混同されていない。

### 運用手順書

- 開始条件、必要権限、確認点、停止条件、復旧、エスカレーションが分かる。
- 破壊的操作の対象と影響を誤認しない記述になっている。

## 指摘化の条件

- 問題のある箇所と、正しい根拠を示せる。
- 読者または運用へ生じる具体的な影響を説明できる。
- 文書だけで確認できない内容は、追加確認事項として分離している。
- 表現上の好みと、正確性や実用性の問題を区別している。
