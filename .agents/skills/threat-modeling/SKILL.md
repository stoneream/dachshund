# 脅威モデリング

対象を攻撃者の視点でモデル化し、実装可能な安全要件と検証へ結び付ける。一度で網羅したとみなさず、設計変更に合わせて更新できる成果物を作る。

## 境界

- 実装計画そのものは `planner`、安全要件をコードや設定へ反映する作業は `software-security-implementation` の範囲とする。
- 既存コードや設定の脆弱性判定は各脆弱性分析スキル、テスト設計は `security-test-design` の範囲とする。
- 利用者が選んでいない方式や製品を、一般的な安全原則だけを根拠に置き換えない。
- 不明な構成を断定せず、モデル化に不足している情報として分離する。
- 脅威の列挙だけで終わらず、守る不変条件、対策の所有者、検証方法まで追跡する。

## 参照

対象範囲と利用者が達成する主要フローを把握した後、モデリング前に[脅威モデリングチェックリスト](references/modeling-checklist.md)を読む。出力前に、入口・出口、権限、業務フロー、残留リスク、更新条件を再確認する。

## 進め方

1. 対象、目的、利用者、依存システム、対象外を定義する。
2. 資産、機微データ、アクター、権限、外部入出力、状態変更を特定する。
3. データフローと制御フローに、信頼境界、入口、出口、既存対策を対応付ける。
4. 通常利用を段階へ分け、攻撃者が入力、順序、回数、アクター、時刻を変える悪用ケースを作る。
5. 各脅威の前提、攻撃経路、影響、既存対策、検知可能性を確認する。
6. 回避、低減、移転、受容の方針を選び、安全上の不変条件と実装責任者へ変換する。
7. 検証方法と残留リスクを定義し、モデルを更新する変更条件を示す。

## 出力

- 対象範囲、前提、対象外
- 資産、アクター、信頼境界、データフロー、攻撃面
- 悪用ケースと脅威。各項目に前提、経路、影響、既存対策を含める
- 採用する対策、安全上の不変条件、対策の所有者
- 検証方法、残留リスク、不足情報、更新条件

図が必要な場合は、構成の見栄えではなく、境界、フロー、アクター、保護策を読める最小の図を選ぶ。
