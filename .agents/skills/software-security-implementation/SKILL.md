# ソフトウェアセキュリティ実装

セキュリティに関係する変更で、守る条件をコード、設定、テスト、CIへ反映する。一般的な対策を一律に当てはめず、対象の設計、利用経路、フレームワーク、既存の防御に合わせて実装する。

## 境界

- 実装前に信頼境界や悪用ケースの整理が必要な場合は `threat-modeling` を使用する。
- 複数のテスト層やリリース判定基準を設計する場合は `security-test-design` を使用する。
- 既存実装で脆弱性が成立するか調べる場合は `software-vulnerability-analysis`、供給経路を分析する場合は `software-supply-chain-analysis` を使用する。
- ホスト、クラウド、ネットワーク、実行基盤の構成は対象外とする。
- 一般論だけを根拠に、利用者が選んでいない方式や製品への置き換えを行わない。
- セキュリティと直接関係しない変更へ、このスキルを一律に適用しない。

## 参照

変更箇所と安全上の不変条件を特定した後、実装前に該当するリファレンスを読む。

- 入力、出力、ファイル、外部接続、API、ブラウザ、クライアントは[アプリケーション境界](references/application-boundaries.md)
- 認証認可、セッション、テナント、秘密情報、機微データ、状態遷移は[認証認可・データ・業務フロー](references/identity-data-and-workflows.md)
- ライブラリ、フレームワーク、生成、動的実行、実行時設定は[依存関係と実行時](references/dependencies-and-runtime.md)
- ソース管理、CI、SBOM、ビルド、成果物、デプロイは[ソース管理・ビルド・配布](references/source-build-and-delivery.md)

変更に関係しないリファレンスまで機械的に適用しない。出力前に、選んだ安全上の不変条件、対策、異常系テスト、残る不確実性を再確認する。

## 進め方

1. 現行の入口、データフロー、権限、状態変更、外部接続、既存対策を確認する。
2. 今回の変更で守る安全上の不変条件と、破られた場合の影響を定義する。
3. 防御を強制する境界を決め、フレームワークや共通処理の既存機能を優先して実装する。
4. 認証認可、入力検証、状態遷移、秘密情報の扱いを、失敗時にも安全な状態へ収束させる。
5. 許可される操作に加え、権限不足、境界値、順序変更、再送、競合、対策失敗をテストする。
6. 既存の静的解析、依存関係検査、テスト、CIの判定を実行し、残る不確実性を分離する。

## 完了条件

- 安全上の不変条件と、それを強制するコードまたは設定を対応付けられる。
- クライアントや呼出し元を信頼しなくても、サーバー側または権限境界で対策が成立する。
- 異常系と回帰条件を自動テスト、または再現可能な検証手順で確認している。
- 変更に不要な権限、外部通信、秘密情報、依存関係を追加していない。
- 実行できない検証と残留リスクを、完了した対策から分離している。
