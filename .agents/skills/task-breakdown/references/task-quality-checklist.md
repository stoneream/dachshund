# タスク品質チェックリスト

入力となるTODO、調査結果、レビュー指摘、作業メモを、着手、レビュー、完了判定が可能な単位へ変換するために使用する。

## 入力の整理

- 元の問題、要望、指摘、決定事項を区別する。
- 事実、推論、未確認事項を区別する。
- 既に完了した事項と未完了事項を分ける。
- 重複、包含、矛盾する項目を確認する。
- 入力元の用語、識別子、参照先を保持する。

## タスクの目的

- 一つのタスクが達成する結果を一文で説明できる。
- 背景ではなく、完了時に変わる状態を目的として書く。
- 方針決定、調査、実装、検証、文書化を必要な場合に分離する。
- 単なる活動ではなく、成果物または確認可能な結果を持たせる。
- 元の依頼へ不要な機能や改善を追加しない。

## 粒度

- 一つの主要成果物または一つの明確な完了条件で閉じられる。
- 責務、影響範囲、必要な専門性が大きく異なる作業を分ける。
- 複数の大きな変更を一つの完了条件へ詰め込まない。
- 単独の成果物がない細かな操作は関連タスクへ統合する。
- タスク数を揃えるためだけに分割または統合しない。

## 境界

- 対象モジュール、文書、設定、データ、運用範囲を必要な精度で示す。
- 対象外を明示しないと誤実装が起きる場合は非対象を記載する。
- 外部システムや別チームの作業を、自分のタスク内の実装として扱わない。
- 既存の未コミット変更や別作業を上書きしない境界を必要な場合に示す。

## 依存関係

- 前提となる決定、調査、実装、外部作業を特定する。
- 成果物を受け取らないと開始できない関係だけを依存として記載する。
- 単に実施しやすい順序を、必須依存として固定しない。
- 循環依存がある場合は、境界または成果物を見直す。
- 並行実行できる項目を、入力に根拠がある範囲で識別する。

## 完了条件

- 実装、設定、文書、調査結果など、確認対象を具体化する。
- 正常系、失敗系、互換性、移行など必要な結果を含める。
- 「適切に対応する」「問題がないこと」だけで終わらせない。
- 実行するテスト、ビルド、レビュー、確認方法を必要な範囲で示す。
- 実行できない検証がある場合は、代替証拠と残る不確実性を示す。

## 調査タスク

- 答える質問、確認する仮説、調査範囲を定義する。
- 参照するコード、文書、ログ、一次情報を必要な範囲で示す。
- 結果の記録先と、後続判断に必要な情報を完了条件へ含める。
- 調査だけで閉じるか、後続タスクを作るかを明確にする。

## 方針決定タスク

- 決める論点、候補、評価基準、決定者を入力から分かる範囲で示す。
- 実装作業を決定タスクへ混在させない。
- 決定結果を記録する成果物と、後続タスクへの接続を示す。
- 決定者が入力で指定されていない場合に、担当者を推測で設定しない。

## 実装タスク

- 変更する責務と維持する契約を示す。
- 必要なテスト、設定、データ移行、文書更新を成果物として含めるか分離する。
- 既存事項の作業分解を越えて、新しい設計判断を確定しない。
- 詳細な設計が未確定の場合は、前提となる設計タスクへ接続する。

## 記載項目

- 説明にはタスクの概要を書く。
- 背景には必要になった理由と入力元を書く。
- 目的には達成する結果を書く。
- 完了条件には閉じるための確認可能な条件を書く。
- 成果物には作成または更新されるものを書く。
- 依存には開始や完了の前提を書く。
- 参照には元文書、コード、指摘、関連タスクを書く。

## 完了確認

- 作業者が追加の設計判断なしで着手できる。
- レビュー者が成果物と完了条件を照合できる。
- 完了または未完了を客観的に判断できる。
- 期限、担当者、優先度、状態を入力なしで補っていない。
- 元の未完了事項をすべて対応付け、追加した項目を識別できる。
