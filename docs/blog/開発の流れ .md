---
title: 開発の流れ
---

## 目的

開発者およびコーディングエージェントが開発を行う際の流れを記している。

## 作業開始時

対象 issue や依頼内容を確認し、変更範囲に関係する文書を読む。
確定済みの仕様、設計判断、開発手順、使い方を確認する場合は `docs/blog` を参照する。
未決事項、作業バックログ、実装前に確認する論点を確認する場合は `docs/discussion` を参照する。

初回セットアップが未実行の場合は `開発環境のセットアップとワークフロー.md` に従って `mise setup` を実行する。

変更を始める前に、どのモジュールと責務に触るかを決める。
既存の責務分離に沿って実装し、境界をまたぐ変更が必要な場合は理由が説明できる状態にする。

## Metals MCPの利用について

コーディングエージェントを使用する場合は、Metals MCP の利用を推奨する。

Scala backend / daemon では、Metals MCP が利用可能な場合、`compile_file`、`compile_module`、`compile_full` などによる diagnostics 確認を `sbt compile` より優先する。
なお、MCPが無効な場合は扱えない検証、整形、生成、または通常の承認が必要な操作は、既存の `sbt` / `mise` 手順に従う。

Metals MCP のセットアップや起動方法は `開発環境のセットアップとワークフロー.md` を参照。

## backend / daemon 変更時

UseCase、step、server endpoint、daemon、daemon handler、DB reader/writer スケルトンを作る場合は、`docs/blog/Codegen の使い方.md` を参照する。
生成前に `--dry-run` で生成予定ファイルと差し込み用コードを確認し、既存ファイルを上書きする場合だけ `--force` を使う。
server endpoint と daemon の生成後は、標準出力に出るスニペットを必要な既存ファイルへ手動で反映する。

```bash
# 実装直後の型エラーや依存の崩れを発見する
sbt compile
```

## backend / daemon 開発終了時

テストを追加、更新、削除する場合は `テスト規約.md` を参照し、backend / daemon の route または handler 境界で何を担保するかを確認する。  
また、`application`、`daemon`、`server` のテストは同じテスト用 DB を共有している。そのためデータの競合が起きるため個別に実行する必要がある。

```bash
# 対象プロジェクトのテストを個別に実行する
sbt application/test
sbt daemon/test
sbt server/test

# もしくは一括で実行する

sbt 'application/test' 'daemon/test' 'server/test'

#  import、未使用コード、設定済みルールによる修正を反映する
sbt scalafixAll

# Scala / sbt / Twirl などの整形を揃える
sbt scalafmtAll
```

## フロントエンド変更時

frontend を変更した場合は、次のコマンドで検査、整形、ビルドを確認する。

```bash
mise front-lint
mise front-format-check
mise front-build
```

## DB 変更時

DB スキーマを変更した場合は、Flyway マイグレーションと tbls スキーマを同期する。

```bash
mise db-down-rm
mise db-up
mise flyway-dev
mise flyway-test
mise tbls-doc
```

DB テーブルメタデータを使うコードを追加または変更した場合は、`docs/blog/Codegen の使い方.md` の手順に従ってメタデータを再生成する。
`tbls/schema` と生成コードの差分を確認し、マイグレーション、スキーマドキュメント、実装の対応がずれていないことを確認する。

## ドキュメント同期

実装によって仕様、設計、実装順、運用手順が変わった場合は、関連する文書も同じ変更で更新する。
確定済みの手順、現況、設計判断は `docs/blog`、未決事項やタスク整理は `docs/discussion` に置く。
一時的な調査や作業中のメモは、用途に応じて `docs/temp` または `docs/working` に置く。

古い前提が残る場合は追記だけで済ませず、現在の実装と矛盾しない形に削除または更新する。

## 完了前の確認

完了前に、実行した検証コマンドと未実行の検証を整理する。
未実行の検証がある場合は、理由と残るリスクを報告する。
