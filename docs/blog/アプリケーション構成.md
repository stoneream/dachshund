## 目的

この文書は、Dachshund のモジュール責務、実装配置、DB アクセス、daemon 実行基盤、ログ方針の現況をまとめる。
新しい機能を追加するときは、この責務分離に沿って配置を決める。

## モジュール責務

| モジュール | 責務 |
| --- | --- |
| `application` | 設定、UseCase、step、DB reader/writer、Spotify / 通知プロバイダークライアント、暗号化、日時などのアプリケーション基盤 |
| `server` | Play Framework の HTTP 入出力、controller、handler、renderer、route |
| `daemon` | 独立した daemon process、ジョブ設定、ジョブスケジューリング、job handler、停止制御 |
| `logging` | ログ出力の共通基盤 |
| `codegen` | UseCase、step、server endpoint、daemon、DB メタデータ、DB アクセサー雛形の生成器 |

`server` と `daemon` は別プロセスとして起動する。
どちらも `application` の設定と UseCase を使うが、`server` から daemon を直接起動しない。

## 実装配置

HTTP endpoint は `Root`、controller、handler、renderer、UseCase の順に追加する。
controller は Play の `Action` と共通エラー処理、handler はリクエストから `UseCaseInput` への変換、renderer は `UseCaseOutput` から `Result` への変換に限定する。
トークン交換、DB 更新、Spotify API 呼び出しなどの業務判断は `application` の UseCase と step に置く。

HTTP request 共通の trace context と user session context は `server` の Action 層で解決する。
ログイン必須の判定は handler 共通処理の権限ポリシーで行い、ログイン必須 UseCase には解決済みの通常ユーザーだけを渡す。
未ログインでも表示する endpoint は、UseCase input に `UserSessionContext` を渡して表示内容を判断する。

UseCase は `application/src/main/scala/io/github/stoneream/dachshund/usecase/...` に置く。
複数の検証、外部 API 呼び出し、DB 更新を含む UseCase は `step` を切り、UseCase 本体は処理順序の制御に集中させる。

外部 API クライアントはプロバイダー単位で `service/spotify` などに置く。
Spotify の有効アクセストークン取得基盤のように複数 UseCase から共有される連携処理も `service/spotify` に置く。
HTTP クライアントの詳細、再試行、レスポンスのデコード、保存済みトークン解決の詳細を UseCase に漏らさない。

## DB アクセス

DB SQL は `application` の `infra/db/.../reader|writer` に閉じる。
reader は参照クエリ、writer は insert/update/delete と状態遷移を担当する。
UseCase、step、daemon、server には SQL を書かない。

DB テーブルメタデータは `codegen` で生成する。
生成手順と制約は `docs/blog/Codegen の使い方.md` を参照する。
監査カラムへ保存するユーザー表現は `docs/blog/監査ユーザー規約.md` を参照する。

トランザクションは `DatabaseTransaction` と `DatabaseRole` を通す。

ブロッキング DB 処理は `DatabaseExecutor`、UseCase の実行制御は `DefaultExecutor`、外部 HTTP などの IO は必要に応じて `IoDispatcher` 相当を使う。

## daemon

daemon は `daemon` プロジェクトの単独エントリーポイントから起動する。
`DaemonMain` は `DaemonModule` で Guice injector を組み、設定読み込み、daemon 用 DB pool 初期化、`JobScheduler` 起動、終了時の後始末を担当する。
daemon 実行時の依存構築は Guice に寄せ、application 層の `@Inject` / `@Singleton` と同じシングルトンの依存グラフを使う。
ジョブ実行、タイムアウト、再試行、executor / DB pool のライフサイクルは ZIO の `Scope` で管理する。

ジョブ実行基盤の責務は次の流れに分ける。

| 段階 | 現在の実装 |
| --- | --- |
| ジョブ定義 | `Job` が `setting` と `dispatch` を定義し、対応する `JobSetting` を持つ |
| スケジューラー | `JobScheduler` が `JobLoader` からジョブを読み、ジョブごとの runner fiber をスコープ付きで起動する |
| ジョブ保存 | `application` のキューテーブルと reader/writer が実行対象、ロック、試行、結果を永続化する |
| ディスパッチ | `Job.dispatch` が 1 回の dispatch を表し、ジョブ定義が `JobHandler.handle` へ委譲する |
| ワーカープール | ZIO fiber とキューの `batchSize` / ロック期限で同時実行範囲を制御する |
| 実行 | `application` の UseCase / step が処理対象として取得済みのデータを処理する |
| 結果 / 再試行 / 要対応 | キュー用 writer が `SCHEDULED`、`PROCESSING`、`SUCCEEDED`、`FAILED`、`BLOCKED`、`SKIPPED` と再試行時刻を保存する |

ジョブの常駐ループ、スケジュール待機、タイムアウト、上限付き再試行、停止時の割り込みは `JobRunner` が管理する。
`JobRunner` は `Job.dispatch` だけを呼び、業務処理の詳細を持たない。
`JobHandler.handle` は 1 回の業務処理だけを担当して `application` の UseCase へ委譲する。
（daemon 側に SQL や外部 API 呼び出しの詳細を置かない。）

ジョブ固有設定は `daemon/src/main/resources/application.conf` を正本にする。

## 設定とログ

アプリケーション設定は `application/src/main/resources/application.conf` に寄せる。
環境変数上書きは既存と同じ `${?ENV_NAME}` 形式に揃える。
daemon 固有の有効化、スケジュール、タイムアウト、再試行、batch size は `daemon/src/main/resources/application.conf` に置く。

秘密値を含む値は設定ファイルに直書きしない。
ログにはトークン、秘密値、パスワード、Spotify user code、Spotify display name、アプリケーションユーザー名、曲名、アーティスト名、アルバム名、プレイリスト名を出していない。
外部 HTTP レスポンス本文や例外メッセージには秘匿値や個人情報が混入する可能性があるため、ログや DB に保存するエラー情報は分類済み error type、HTTP status、件数、内部 ID に限定する。

## 変更時の確認

backend / daemon を変更した場合は `docs/blog/開発の流れ .md` に従って検証する。
DB スキーマを変更した場合は Flyway マイグレーション、`tbls/schema`、DB メタデータの同期を同じ変更で確認する。
