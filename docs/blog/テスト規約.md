---
title: テスト規約
---

## 目的

この文書は、Dachshund のテストを追加、更新、削除するときの判断基準を記す。
テストは、各モジュールの責務境界で入力、出力、副作用、時刻などの重要な振る舞いを説明できる状態に保つために書く。

## テストを書く前に決めること

まず、どの責務境界で振る舞いを確認するかを決める。
呼び出し元から見えるリクエスト、入力、実行結果、エラーを境界で確認する。

server endpoint は、route ごとに HTTP リクエストからレスポンスまでを検証する。
daemon は、handler から処理結果や観測可能な副作用までを一気通貫で検証する。
server endpoint や daemon handler から到達できる UseCase は、route または handler 境界で検証する。
UseCase 配下の step の振る舞いは、呼び出し元の責務境界から検証する。

サービスやユーティリティは例外として、対象の責務を小さく切り出して検証する。
変換、計算、暗号化、文字列処理など、責務が独立している処理は、そのクラスや関数の公開された振る舞いを直接テストする。

## 新しくテストを追加する場合

新しいテストは、利用者または呼び出し元から見える振る舞いを表す。
正常系では入力、出力、永続化結果、ログなど、対象の責務から観測できる結果を確認する。
異常系では失敗することだけでなく、どの入力や状態が不正として扱われるかを確認する。

DB を使う場合は実テスト用 DB を使い、外部 API、時刻、設定などの DB 以外の依存は Mockito やテスト内の小さな代替実装で差し替える。
固定した前提で再現できるテストにする。

## 既存テストを更新・削除する場合

既存の処理を置き換える場合は、現在の仕様を表すテストへ更新する。
削除するテストがある場合は、同じ振る舞いを担保するテスト、または削除後に残る仕様の確認先を明確にする。

正常系と異常系は、各 `Scenario` で前提条件が読み取れる fixture にする。
fixture の共有によって前提条件が読み取りにくくなる場合は、各 `Scenario` 内で前提を明示する。

複数のテストで同じ準備処理、assert、リクエスト作成、固定時刻、設定生成が必要になった場合は、共通のテストユーティリティを作成する。
共通化したテストユーティリティは、テストの意図が伝わる名前と引数にし、各 `Scenario` の前提が読み取れる状態に保つ。

## server endpoint をテストする場合

server endpoint のテストでは、route ごとに HTTP リクエストからレスポンスまでを検証する。
クエリ文字列、cookie、リクエスト本文、パスパラメータ、現在日時など、route 配下の処理が解釈または注入する値に加えて、UseCase の結果がレスポンスに反映されることを確認する。

server endpoint のように Play application が DB connection pool を初期化するテストは `PlayApplicationDatabaseSupport` を利用する。
Play application の起動後に、各 `Scenario` の開始前と終了後に DB をクリアする。

## daemon handler / DaemonMain をテストする場合

daemon handler のテストでは、handler の実行開始から処理結果、ログや repository 更新などの観測可能な副作用までを一気通貫で検証する。
daemon handler の責務として外部から確認できる振る舞いを対象にする。

daemon 起動時の readiness のように `DaemonMain` から実行される処理は、daemon 起動境界で検証する。

## サービス・ユーティリティをテストする場合

サービスやユーティリティは、対象のクラスや関数が公開している振る舞いを直接テストする。
変換、計算、暗号化、文字列処理など、責務が独立している処理は、この粒度で検証する。

必要な依存は Mockito、専用 trait や interface、またはテスト用実装で満たす。
コンストラクタの依存が大きい場合は、専用 trait や interface への分離を検討する。

## DB を使う場合

DB は実テスト用 DB を使って検証する。
DB に依存するテストは `DatabaseSupport` を利用し、各 `Scenario` の開始前と終了後に DB をクリアする。

前提データは、各テストの `Scenario` から読める位置に定義する。
各レコードは `*Source` や既存 domain object として明示し、`toXxxDbRow` で生成済みの `*DbRow` に変換してから、本番コードの DB writer に `writer.write(row)` で渡す。
insert で DB が採番する `id` は、`toXxxDbRow` 側で generated row の未使用値として扱う。
対象テーブルの generated row が未生成の場合は、codegen で `*DbRow` を生成する。

ID 依存のレコードは、依存先 ID が生成された後に別の source record として定義する。
各テストレコードの状態は `Scenario` 内で明示する。

読み取り結果の検証が必要な場合は、対象テストの近くに小さなクエリを置き、期待する DB 状態をそのテスト内で読み取れるようにする。

## 時刻を扱う場合

現在日時を使う handler やサービスのテストでは、Mockito で `DateTimeService#now` をスタブ化し、固定した `BusinessDateTime` を返すようにする。
`DateTimeService#now` の呼び出し検証や例外など、単純な固定時刻以外の協調動作が必要な場合も Mockito で明示する。
UseCase の入力に現在日時が含まれる場合は、`UseCaseInput` に固定した `BusinessDateTime` を直接渡す。

時刻に依存する期待値は、固定した `BusinessDateTime` から組み立てる。

## エラーケースを書く場合

入力不備を検証するテストでは、失敗することだけでなく、どのパラメータが不正として扱われるかを確認する。
たとえば controller 層で `ControllerError.InvalidParameter` を期待する場合は、対象の `param` も検証する。

エラーケースでも、利用者または呼び出し元から見える振る舞いを確認する。

## 依存を差し替える場合

DB 以外の依存の差し替えには Mockito を優先して使う。
戻り値、例外、呼び出し回数など、テスト対象から見える協調動作を明示できるため、手書きの fake、stub、capturing class よりも優先する。

手書きの代替実装は、Mockito では意図が読みにくい場合や、入力を保持して後続の検証に使う場合に限って使う。
その場合は、原則としてテスト内の private class または private method として定義する。

## テスト名・検証・fixture の書き方

テストは ScalaTest の `Feature` / `Scenario` で書く。
テスト名と `Feature` / `Scenario` は、利用者または呼び出し元から見える振る舞いを表す。
日本語で書く場合は、「何を渡す」「何で失敗する」「何を返す」のように期待結果が読み取れる表現にする。

期待値の検証では、ScalaTest の matcher よりも `assert` を優先する。
matcher を使う場合は、`OptionValues` や `ScalaFutures` など、テストの前提を読みやすくするために必要な範囲に留める。

fixture は、各 `Scenario` の前提が読み取れる範囲で使う。
共通 fixture が状態や意図を隠す場合は、重複を許容してテスト内に明示する。

## 実行と整形

backend / daemon のテスト変更後は、基本的に `sbt test` を実行する。
変更範囲が小さくても、モジュール間のテスト依存関係や scalac オプションの影響を受けるため、完了前には少なくとも該当モジュールのテストを実行する。

テストコードも本体コードと同じく scalafmt と scalafix の対象にする。
import の追加、削除、未使用警告、整形崩れがある場合は、`sbt scalafixAll` と `sbt scalafmtAll` を実行してから差分を確認する。
